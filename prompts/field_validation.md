# Field-validation notebooks: one end-to-end pipeline notebook per subset

## Goals

Build a set of validation notebooks, one per calculated-field subset, at::

    notebooks/notebooks_field_validation/surface_fields/{subset}.ipynb
    notebooks/notebooks_field_validation/depth_fields/{subset}.ipynb

Each notebook shows the COMPLETE end-to-end pipeline for every final field
in its subset: the raw inputs, the shared intermediate calculations, and
the final fields — with standardized maps, PDFs, depth diagnostics
(DEPTH), and a placeholder for field-specific literature validation.

Notebooks are organized by SUBSET (not per field) because fields within a
subset share raw inputs and intermediates (e.g. ``stratification``:
Theta/Salt → sigma0 → {MLD, N², ml_heat_content}).  Shared intermediates
are computed once; their diagnostics repeat wherever needed so each
field's pipeline reads standalone.

  one-line reference.

## 3. Data loading strategy

UPDATED 2026-07-31: notebooks GENERATE their own data before loading
it.  Each notebook first RUNS the pipeline for its subset + timestep
(template step 1; likely one new .yaml config per subset, drawing on
``notebooks/notebooks_global/running_generate_global_script.ipynb``),
then LOADS the freshly generated store (template step 2, drawing on
``notebooks/notebooks_global/assess_generate_global_script.ipynb``).
This makes the notebooks re-runnable validators after any future code
change — Route A below reads the notebook-generated store, not a
historical run.  Generation timestep: **20121109T12 for BOTH the
surface and depth cases**.

Two clearly distinguished routes:

**Route A — 2D products, loaded directly.**  Final-field global maps and
regional 2D subsets come from the produced zarr stores via
``GlobalZarrDatasetReader.get_channel_snapshot(t, channel)`` with
coordinates/land mask from ``GlobalGridZarrReader`` (lon, lat,
land_mask).  Row A (global) downsampled ``[::12, ::12]``; regional rows
sliced from the rectangular grid by named-region bounding boxes
(regions module, Section 5).  Raw/intermediate 2D fields for the SURF
figures are computed LIVE in the notebook from the OSN/S3 snapshot via
``calculate_fields`` (cheap for 2D; guarantees the intermediates match
the code being validated).  ⚠ Existing stores were generated
PRE-migration; see Clarification 1.

**Route B — 3D data, via the tiles workflow ONLY.**  Never load global
3D DEPTH data in a notebook.  All vertical profiles, cross-sections, and
any 3D intermediate diagnostics come from single-face 720×720×51 tiles
(≈1400×1400 km, full water column) obtained through
``dbof.tiles.tile_utils``.

Existing (reuse as-is):

- ``tile_mapping.rect_ij_to_tile(i, j) → TileInfo`` — 432 fixed tiles on
  the rect grid; guarantees single-face, chunk-aligned 720×720 slices
  (face idx + face-local j/i slices).
- ``tile_utils.latlon_to_rect_ij(lon, lat)`` — geographic tile selection.
- ``tile_utils._load_grid_for_tile`` — tile-extent grid (XC, YC 2D; Z 1D;
  hFacC for the land mask; metrics available from the grid store).
- ``tile_utils._load_tracers_for_tile`` — lazy S3 read of requested vars
  for one face, sliced to the tile, dims (face=1, k=51, j=720, i=720).
- ``TILE_PROPERTIES`` registry + ``compute_tile_property`` +
  ``_build_output_dataset`` (XC/YC/Z coords, provenance attrs, NetCDF)
  + ``run()`` end-to-end (by rect pixel or lon/lat), with QA plot.

Current registry limitation: ``TILE_PROPERTIES`` = {density,
temperature, salinity} and ``vars_needed`` covers tracers only.  Minimal
eventual extensions (NOT built yet):

1. A ``raw_3d`` tile property (or per-variable entries) for U, V, W —
   ``_load_tracers_for_tile`` already accepts arbitrary ``vars_needed``;
   the gap is registry entries + handling staggered dims (i_g/j_g/k_l)
   at the tile boundary (one extra edge column/row or accept N−1).
2. A "tile ds_merge" helper that merges tile tracers + tile grid and
   builds a LOCAL xgcm grid (``use_connections=False`` — a single face
   has no face_connections).  Consequence: gradient-based fields are
   edge-contaminated in a ~3-cell rim (same as the synthetic-test
   EDGE_MARGIN); notebooks trim the rim before plotting.  Interior of a
   720² tile is unaffected.
3. Optionally: register final-field tile properties (N2, MLD, Ri, ...)
   pointing at the existing CFAD functions — they are dimension-agnostic
   and lazy, so ``compute=`` wiring is one line each (the density entry
   already demonstrates the pattern with
   ``calculate_fields.potential_density_anomaly``).

Answers to the specific tile questions:

- Region/tile specification: by ``lon/lat`` (preferred for notebooks) or
  rect pixel; tile dims are FIXED at 720×720×51 on one face — a tile
  SAMPLES a validation region, it does not cover it.  Each region
  therefore gets its own representative tile (Section 6).
- Raw variables per subset tile: stratification/frontal Θ,S;
  vertical_shear/kinematic/mixing +U,V; ertel_pv/buoyancy_fluxes
  +U,V,W; energetics Θ,S (+YC from grid).
- Intermediates/finals from tiled data: via the same ``calculate_fields``
  / ``calculate_fields_at_depth`` functions on the tile ds_merge (they
  are dimension-agnostic; proven by tests/test_calculate_fields.py).
- sfc / z25m / MLD diagnostics from ONE tile: yes — k=0 slice, nearest-k
  to 25 m (``VH._nearest_k_to_depth``), and MLD extraction
  (``depth_strategies`` / ``VH._extract_at_mld``) all operate on the
  same tile volume.  This also cross-checks Route A: the tile's suffix
  slices should match the corresponding region of the 2D product maps.
- Metadata: retained (XC/YC/Z coords, hFacC mask, attrs) by the existing
  ``_build_output_dataset`` pattern.
- Coverage: one tile per region; profiles AND cross-sections both come
  from the same tile (Section 6).
