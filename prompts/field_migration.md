# Migrate calculated-field modules to a single-implementation structure

## Goals

Consolidate `calculate_additional_fields.py` and
`calculated_fields_at_depth.py` so that every physical field has exactly ONE
implementation:

- `src/dbof/preprocessing/calculate_fields.py` (renamed from
  `calculate_additional_fields.py`) — home for ALL baseline field functions
  in lazy, dimension-agnostic form. These work identically on inputs with or
  without a `k` dimension.
- `src/dbof/preprocessing/calculate_fields_at_depth.py` (renamed from
  `calculated_fields_at_depth.py`) — ONLY fields that require vertical
  structure (`k`, `W`, vertical spacing). Imports from `calculate_fields`,
  never the reverse.
- The SURF/OSN vs DEPTH pipeline distinction lives only in the application
  layer (`surface_subsets.py`, `depth_subsets.py`), which is unchanged in
  role. Fields with inherently 2D inputs (Eta, wind stress) live in
  `calculate_fields.py` — the code is dimension-agnostic; the inputs just
  happen to be 2D.

Examine the code in llc4320-native-grid-preprocessing/src/dbof with emphasis
on:

- `preprocessing/calculate_additional_fields.py` (surface-era module)

  `test_generate_tile.py`)

## Migration rules

These apply to every function that lands in `calculate_fields.py` or
`calculate_fields_at_depth.py`:

- Drop the `_3d` suffix. Dimensionality is a property of the input, not the
  function.
- Fully lazy: no `.persist()` or `.compute()` inside field functions.
  Materialisation is an application-layer decision (the single
  `dask.compute()` in `surface_subsets.py` already fuses shared graphs).
- No `.copy(deep=True)` on inputs.
- `xr.where`, never `np.where` (preserves coords/attrs and laziness).
- Keep the optional pre-computed-intermediate kwargs pattern
  (`jacobian=`, `buoyancy_gradients=`, `n2=`, ...) where it already exists.

## Phase 1 — Density, buoyancy, and grad_squared plumbing

### Resolved definitions (apply throughout)

**Density.** JMD95 computes in-situ density rho(S, Theta, p), but every
call in this repo passes p=0 — which is, by definition, potential density
referenced to the surface. So `_density_lazy` / `density_of_field` already
return surface-referenced potential density; their "in-situ density"
docstrings are a misnomer to fix during the move. Structure going forward:

- `potential_density(ds_merge)` — surface-referenced potential density
  rho_theta = JMD95(S, Theta, p=0), lazy. Named for what it actually is
  (the legacy name `density_of_field` was a misnomer below the surface).
  Docstring notes: equals in-situ density only at the surface; evaluating
  the EOS at p = p_ref with potential temperature is the standard
  potential-density construction (TEOS-10, CSIRO seawater `pden`, and the
  Bodner submeso_param_net LLC4320 preprocessing all do exactly this).
- `potential_density_anomaly(ds_merge)` — thin wrapper:
  `potential_density(ds_merge) − SIGMA0_REFERENCE_DENSITY` (sigma0). The
  ONLY difference is the −1000 offset plus name/attrs; implement one via
  the other, exactly as `potential_density_anomaly_3d` already does with
  `_density_lazy`.
- Note in docstrings: N², density gradients, and MLD are therefore all
  sigma0-based. Standard upper-ocean practice (strictly N² wants locally
  referenced potential density; the sigma0 approximation is fine near the
  surface, biases grow at depth).

**Buoyancy.** ONE definition everywhere:

    b = G * rho / RHO0        [m s^-2]

- Eliminate the `G_KM * rho / rho_ref * 1e3` route entirely. It is
  algebraically just g in km/s^2 undone by the 1e3 — except it bakes in
  g = 9.8 instead of G = 9.81. Delete `G_KM` from `physical_constants.py`.
- The legacy scaled buoyancy (`buoyancy_of_field*1e3` == `buoyancy_field_3d`
  == 9.8*rho/1025) and the "phys" buoyancy (9.81*rho/1000) therefore
  differed in TWO constants: g (0.1%) and rho_ref (2.5%). Both collapse
  into the single formula above; `buoyancy_phys` ceases to exist as a
  separate concept.
- `RHO0 = 1000.0 kg/m^3` (DECIDED) — the single reference density used
  by buoyancy, N², and everything derived from them, throughout the
  codebase. Matches the Bodner submeso_param_net LLC4320 preprocessing.
  `RHO0_BOUSSINESQ` already holds this value and becomes the one
  reference-density constant; RETIRE `RHO0_SEAWATER` (1025), switching
  its remaining uses (Turner angle linear-EOS identity, legacy buoyancy)
  to `RHO0_BOUSSINESQ`.
- Consequences: dimensionless diagnostics (R_ib, W*, Turner angle) are
  unaffected — the (G/RHO0)^2 factors cancel when numerator and
  denominator share the definition (the point of consolidating).
  Dimensional outputs (buoyancy channel, grad_b2, N², frontogenesis)
  shift by a uniform ~2.5–3% relative to legacy values; the Phase 0
  golden regression must expect this known, constant rescaling.
- `b` is not an anomaly and carries no negative sign (fine — all uses are
  gradients/vertical derivatives where the offset vanishes); fix the
  `physical_constants.py` docstring that claims b = −g rho/rho_ref.
- `surface_subsets.py` must NOT recalculate buoyancy or density; its
  "density"/"buoyancy" channels call `calculate_fields.potential_density`
  and `calculate_fields.buoyancy_of_field` directly (output channel keys
  unchanged).

**Deferred (noted, not part of this migration):**

- `pressure_from_depth(Z)` utility for any future in-situ density need:
  Boussinesq-consistent p[dbar] = RHO0 * G * |Z| / 1e4 (LLC4320 provides
  Z, not pressure).
- Locally-referenced potential density for N² at depth (evaluate JMD95 at
  each level's own p(z) for the vertical difference) to remove the
  thermobaric bias of surface-referenced sigma0 deep in the column.

### Steps

1. LEAVE `physical_calculations.density_of_field` and `buoyancy_of_field`
   in place, unchanged (legacy, `.persist()`-based). Add a docstring note
   that they are legacy and superseded. After this migration nothing in
   `src/` calls them. Current call sites that must switch to the new lazy
   versions (5 total):
   - `calculate_additional_fields.compute_buoyancy_gradients` (L145)
   - `calculate_additional_fields.grad_b2` (L176)
   - `calculate_additional_fields.grad_rho2` (L231)
   - `surface_subsets.py` "density" channel (L127)
   - `surface_subsets.py` "buoyancy" channel (L129)
2. Add lazy `potential_density(ds_merge)` and `buoyancy_of_field(ds_merge)`
   near the top (~L16) of `calculate_fields.py`, modelled on
   `calculated_fields_at_depth._density_lazy` (apply_ufunc,
   `dask="parallelized"`) but WITHOUT the hard-coded `chunk_spec`, and
   implementing the resolved definitions above (potential-density naming,
   b = G*rho/RHO0).
   - Why the chunk_spec existed only in `_density_lazy`: density is the
     common ancestor of nearly every depth graph (N², MLD, gradients,
     R_ib all start from it), so it was a convenient single choke point.
     It served two purposes: (a) the JMD95 `apply_ufunc` needs `Theta`
     and `Salt` chunk-aligned, and merged zarr subsets arrive irregularly
     chunked per variable; (b) `k: -1` makes columns contiguous so
     downstream vertical derivatives / MLD reductions don't rechunk
     mid-graph. Other depth properties never needed it because they
     consume density's already-well-chunked output or tolerate irregular
     chunks.
   - Where it goes instead (DECIDED): a small helper
     `_ensure_depth_chunking(ds_merge)` in `depth_subsets.py`, applied
     once at the top of each `compute_*` entry point — the same boundary
     that owns the single `dask.compute()`. This fixes chunking for ALL
     fields (not just density-descended ones) and keeps
     `calculate_fields.py` chunking-agnostic. It is a pipeline
     performance concern, not field math.
3. Move `physical_calculations.grad_squared` to
   `utils/native_gradient.py` (it is a pure operation on gradient
   components — zonal² + merid² — not specific to any property). Update its
   5 call sites (grad_b2, grad_rho2, grad_theta2, grad_salt2, grad_eta2 in
   `calculate_additional_fields.py`). Leave a re-export or deprecation note
   in `physical_calculations.py` if anything external imports it.
4. Delete `_grad_squared_3d` from the depth module (it conflates two steps:
   field → components → squares). The single canonical gradient workflow
   everywhere becomes:

   ```
   components = ng.calculate_native_gradient_tracer(field, ds_merge, grid)
   grad2      = ng.grad_squared(*components)
   ```

   ONE native-gradient function (raw field → vector components) and ONE
   grad-squared function (components → scalar), both in
   `native_gradient.py`.

### Buoyancy-gradient consolidation

Current state (worst-case scattering) — five overlapping routes to a
buoyancy gradient:

1. `calculate_additional_fields.compute_buoyancy_gradients` → components
   (`BuoyancyGradients`), used by the frontogenesis functions. KEEP this
   role.
2. `calculate_additional_fields.grad_b2` → recomputes buoyancy + gradient
   itself instead of using (1).
3. `calculated_fields_at_depth.compute_buoyancy_gradients_3d` → duplicate
   of (1) on `buoyancy_field_3d`.
4. `calculated_fields_at_depth._buoyancy_gradient_phys_3d` (+
   `_buoyancy_gradient_squared_phys_3d`) → components on a DIFFERENT,
   unscaled buoyancy (`(G/RHO0_BOUSSINESQ)·rho`), used by
   `balanced_richardson_number_3d` and `modified_okubo_weiss_3d`.
5. `calculated_fields_at_depth.grad_b2_3d` → `buoyancy_field_3d` +
   `_grad_squared_3d`.

Target state — ONE buoyancy definition (Phase 1: b = G*rho/RHO0), ONE
gradient machine, ONE application to buoyancy:

- `compute_buoyancy_gradients(ds_merge, grid)` in `calculate_fields.py`
  returns `BuoyancyGradients(zonal, merid)` from
  `buoyancy_of_field(ds_merge)`. This keeps the namedtuple structure the
  frontogenesis functions rely on; routes (3) and (4) delete outright —
  with a single buoyancy definition there is no longer any reason for a
  separate "phys" gradient path.
- `grad_b2(ds_merge, grid, buoyancy_gradients=None)` =
  `ng.grad_squared(*components)`, reusing (1)'s output via the standard
  injection kwarg. Routes (2) and (5) collapse into this.
- `balanced_richardson_number` and `modified_okubo_weiss` call the same
  `compute_buoyancy_gradients` — automatically N²-consistent because N²
  now uses the same G/RHO0. No private phys-gradient helpers.
